Two products, two ways in

Web automation

Requirement-first

Seven sources — Jira, Azure DevOps, Confluence, SharePoint, a document, pasted text or the app itself — become requirements a person reads before anything is planned.

API automation, before

Spec-first

Thirteen import methods — OpenAPI, Postman, cURL, HAR and the rest — become an endpoint catalogue that goes straight to the planner.

A spec says what an endpoint accepts. It does not say what the business expects of it.

So there was nowhere to record an endpoint’s purpose or its rules, nothing tying a test back to a spec section or a Jira key, no point at which a person could reject an item before planning, and no record that a feature had been exercised in a customer-similar environment.

The screenshot that started this was the Web flow’s source picker. The question was what API Automation would need to work the same way. The answer was not “copy the picker” — API Automation already has thirteen ways in, more than Web. What it lacked was the layer between the import and the planner.
